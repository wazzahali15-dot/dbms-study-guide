Data Models & Architecture

Chapter 2 — DB System Concepts, Schema, Three-Schema Architecture, DBMS Languages

What is a Data Model?

A Data Model is a formal set of concepts used to describe:

📐 Structure

How data is organized — tables, columns, data types, relationships between data.

⚙️ Operations

What can be done with data — insert, update, delete, retrieve, compute.

🔒 Constraints

Rules the data must follow — uniqueness, not-null, valid ranges, referential rules.

Simple Analogy
A data model is like the blueprint of a building. The blueprint (data model) defines the structure — without it, you can't build consistently.

Categories of Data Models

CategoryLevelWho Uses ItExample
Conceptual (High-Level)Close to user thinkingEnd users, business analystsEntity-Relationship (ER) Model
Implementation (Middle)Between conceptual & physicalApplication developers, DBAsRelational Model (SQL tables)
Physical (Low-Level)How data sits on diskDBMS engine internallyFile structures, indexes, access paths

Schema vs. Instance

Schema (Intension)

The design/structure of the database — table names, column names, data types, constraints. Changes very rarely. Like the blueprint of a house.

Instance / State (Extension)

The actual data stored at a specific point in time. Changes every time data is inserted, updated, or deleted. Like the house at a given moment.

Exam Tip
Schema = Intension (stays fixed). Instance/State = Extension (changes constantly). "The database schema changes rarely; the database state changes every time the database is updated."

Three-Schema Architecture

Proposed to support program-data independence and multiple user views. The database has 3 levels of schema:

External Level

Different users see different views of the data. Each user/application has its own external schema (what it can see and access).

Conceptual Level

Describes the entire database structure and all constraints for the whole community of users. Most important for DBAs.

Internal Level

Describes exactly how data is stored on disk — file organization, indexes, access paths, compression.

Data Independence

🔷 Logical Data Independence

You can change the conceptual schema without changing the external schemas or application programs.
Example: Adding a new column to a table doesn't break existing views.

🔷 Physical Data Independence

You can change the internal schema (e.g., add a new index, change file structure) without changing the conceptual schema.
Example: Creating a new index for performance doesn't affect the table structure.

Why it matters
Data independence means changes at lower levels don't break higher levels. Only the mapping between levels needs to be updated. Application programs don't need to be rewritten.

DML (Data Manipulation Language) is used to retrieve and manipulate data in the database. Examples: SELECT, INSERT, UPDATE, DELETE. DML can be high-level (SQL — declarative, set-oriented) or low-level (procedural, one record at a time).

3. Three-Tier Client-Server: Client → Application/Web Server (business logic) → DB Server. Most secure because clients never directly access the database. Used in modern web applications.

The Relational Model was proposed by E.F. Codd of IBM in 1970. First commercial systems appeared in 1981–82. Three commercial RDBMS products: Oracle, Microsoft SQL Server, IBM DB2. Free open-source examples: MySQL, PostgreSQL.

Relational Databases

Keys, Functional Dependency, Integrity Rules, Relational Schema

What is a Relation?

A Relation is a two-dimensional table made of rows (tuples) and columns (attributes). It is the core structure of the Relational Model, based on mathematical set theory.

Key Equation
Relation = Entity Set = Table = Dataset (in MS Access)

Characteristics of a Relational Table

1
Two-Dimensional Structure

Composed of rows and columns. A table has a fixed set of columns but a variable number of rows.

2
Row = One Entity Occurrence (Tuple)

Each row represents one unique record. Example: One row in STUDENT = one student.

3
Each Column = One Attribute with a Unique Name

Columns represent properties. Example: STU_NUM, STU_LNAME, STU_FNAME, STU_DOB.

4
One Value per Cell

Each row/column intersection holds exactly ONE atomic value. No lists or sets in a single cell.

5
Same Data Type per Column

All values in a column must be of the same type and from the same domain (allowed value set).

6
Order Doesn't Matter

The order of rows and columns is irrelevant to the DBMS — same data regardless of order.

7
Every Table Must Have a Primary Key

Some attribute (or combination) must uniquely identify each row. No two rows can be identical.

Types of Keys

Key TypeDefinitionExample
Super KeyAny attribute or combination that uniquely identifies every row.STU_NUM alone; or {STU_NUM, STU_LNAME}; or {STU_NUM, STU_FNAME, STU_DOB}
Candidate KeyA minimal super key — no extra unnecessary attributes. Cannot remove any attribute and still have uniqueness.STU_NUM (sufficient alone). {STU_NUM, STU_LNAME} is NOT a candidate key — STU_LNAME is unnecessary.
Primary Key (PK)The candidate key chosen as the official row identifier. CANNOT be NULL.STU_NUM chosen as PK. Underlined in schema notation.
Foreign Key (FK)Attribute in one table whose values must match a PK in another table OR be NULL. Links tables together.VEND_CODE in PRODUCT table references VEND_CODE (PK) in VENDOR table.
Composite KeyA key composed of two or more attributes together.{STU_FNAME, STU_LNAME, STU_DOB} — together they might be unique.
Secondary KeyAn attribute used for data retrieval only. Does NOT guarantee uniqueness.Customer phone — same phone can match multiple people (family).

Functional Dependency (FD)

Attribute B is functionally dependent on A (written A → B) if each value of A determines exactly ONE value of B.

STU_NUM → STU_LNAME, STU_FNAME, STU_DOB, STU_PHONE

Read: "STU_NUM determines (uniquely identifies) STU_LNAME, STU_FNAME, STU_DOB, STU_PHONE"

Key Insight
The principle "A determines B" (A → B) means: if you know A, you can look up exactly one B. If two rows have the same A, they MUST have the same B.

Example: STU_NUM → STU_PHONE means knowing the student ID gives you exactly one phone number. But STU_PHONE → STU_NUM is NOT an FD — two students can share the same phone (roommates), so phone doesn't uniquely determine the student.

Full Functional Dependency

When B depends on the entire composite key A — you cannot remove any attribute from A and still determine B.

{STU_FNAME, STU_LNAME, STU_DOB} → STU_GPA   (Full FD — all three needed)

NULL Values

❌ NULL ≠ Zero

Zero is a numeric value. NULL means "no value exists at all."

❌ NULL ≠ Space

A space is a character. NULL is the complete absence of any value.

✅ NULL = No Value

Created when a field is left empty. Cannot be part of a Primary Key.

NULL can represent three different situations:

  1. Unknown value — the value exists but we don't know it.
  2. Known but missing — we know there should be a value but it hasn't been entered.
  3. "Not applicable" — the attribute doesn't apply to this entity (e.g., STU_INIT for a student with no middle initial).
Warning
NULL creates problems with aggregate functions like COUNT, AVG, SUM — they ignore NULLs. NULLs also cause issues when linking tables via joins.

Integrity Rules

🔵 Entity Integrity Rule

Requirement: All primary key entries must be unique AND no part of a primary key may be NULL.

Purpose: Ensures every row can be uniquely identified, so foreign keys can properly reference them.

Example: No two invoices can have the same invoice number, and no invoice can have a null invoice number.

🟢 Referential Integrity Rule

Requirement: A foreign key must either match an existing primary key in the referenced table OR be NULL (if not part of its own PK).

Purpose: Prevents "orphan" records — you can't have an order referencing a customer who doesn't exist.

Example: You cannot add an order with CustomerID=99 if customer 99 doesn't exist in the CUSTOMER table.

Relational Schema Notation

A textual way to represent a database. Each table shown with its name and attributes in parentheses. Primary key is underlined.

Example Schema
VENDOR (VEND_CODE, VEND_CONTACT, VEND_PHONE)
PRODUCT (PROD_CODE, PROD_DESCRIPT, PROD_PRICE, PROD_ON_HAND, VEND_CODE)

Here: VEND_CODE in PRODUCT is a Foreign Key referencing VENDOR's primary key VEND_CODE.
The link is created because both tables share the VEND_CODE attribute with common values.

NOT NULL and UNIQUE Constraints

NOT NULL Constraint

A column must always have a value — it cannot be left empty. Applied to required fields.
Example: STU_LNAME NOT NULL — every student must have a last name.

UNIQUE Constraint

No two rows can have the same value in this column. Unlike PK, UNIQUE columns CAN be NULL (unless combined with NOT NULL).
Example: Email address must be unique per customer.

📋 Chapter 4 Summary

  • A Relation = two-dimensional table. Each row = one entity occurrence (tuple). Each column = one attribute.
  • Super Key ⊇ Candidate Key ⊇ Primary Key. PK = the chosen candidate key, never NULL.
  • Foreign Key must match an existing PK in the referenced table OR be NULL. Links tables.
  • Functional Dependency A → B: knowing A gives you exactly one B. Foundation of normalization.
  • NULL = no value at all. NOT zero, NOT space. Cannot be in PK. Causes problems with aggregates.
  • Entity Integrity: PK must be unique and NOT NULL. Referential Integrity: FK must match existing PK or be NULL.
  • NOT NULL constraint: column must always have a value. UNIQUE constraint: no duplicate values.

❓ Chapter 4 — Q&A

1What is a Relation? List any four characteristics of a relational table.
A Relation is a two-dimensional table composed of rows and columns used to store data in the relational model. Four characteristics: (1) Each row (tuple) represents one unique entity occurrence. (2) Each column represents one attribute with a distinct name. (3) Each row/column intersection contains exactly one atomic (single) value. (4) All values in a column must conform to the same data type. (5) The order of rows and columns is irrelevant to the DBMS. (6) Each table must have a Primary Key.
2Distinguish between Super Key, Candidate Key, and Primary Key.
Super Key: Any attribute or combination of attributes that uniquely identifies every row in a table. Example: {STU_NUM}, {STU_NUM, STU_LNAME}, {STU_NUM, STU_FNAME, STU_DOB}.
Candidate Key: A minimal super key — no unnecessary attributes. You cannot remove any attribute and still have uniqueness. Example: STU_NUM alone qualifies; {STU_NUM, STU_LNAME} does NOT (STU_LNAME is redundant).
Primary Key: The candidate key chosen as the official unique identifier. Cannot be NULL. Every table has exactly one primary key.
3Define Functional Dependency with an example. Is STU_PHONE → STU_NUM an FD?
A Functional Dependency A → B means: knowing the value of attribute A determines exactly one value of attribute B. If two rows have the same A, they must have the same B.
Example: STU_NUM → STU_LNAME (knowing student number gives exactly one last name).
STU_PHONE → STU_NUM is NOT a valid FD because two students could be roommates and share the same phone number. So one phone number could point to multiple students — it doesn't uniquely determine STU_NUM.
4What is NULL? Why can't it be part of a Primary Key?
NULL is the complete absence of a value — it is NOT zero, NOT a blank space. It's created when a field is left empty (pressing Enter/Tab without entering anything). NULL cannot be part of a Primary Key because the Primary Key must uniquely identify every row — if the PK were NULL, you couldn't identify that row or reference it reliably from other tables via foreign keys. This is the Entity Integrity Rule.
5State the Entity Integrity Rule and the Referential Integrity Rule.
Entity Integrity Rule: All primary key entries must be unique and no part of a primary key may be NULL. This ensures every row has a unique identity and can be properly referenced.
Referential Integrity Rule: A foreign key must either (a) match an existing primary key value in the referenced table, OR (b) be NULL (if not part of its own table's PK). This prevents orphan records — you cannot have a foreign key pointing to a non-existent primary key.
6What is a Foreign Key? Write a relational schema example showing a FK relationship.
A Foreign Key is an attribute in one table whose values must match the Primary Key values in another table (or be NULL). It creates a link between two tables.
Example:
VENDOR (VEND_CODE, VEND_NAME, VEND_PHONE)
PRODUCT (PROD_CODE, PROD_NAME, PROD_PRICE, VEND_CODE)
Here, VEND_CODE in PRODUCT is a FK referencing VENDOR's PK. Every VEND_CODE in PRODUCT must exist as a VEND_CODE in VENDOR, or be NULL.
7What is the difference between NOT NULL and UNIQUE constraints?
NOT NULL: Ensures that a column must always have a value — it cannot be left empty. Example: StudentName NOT NULL means every student must have a name.
UNIQUE: Ensures no two rows can have the same value in that column. Unlike Primary Key, UNIQUE columns can contain NULL values (unless also marked NOT NULL). Example: Email UNIQUE means no two customers can share the same email address.

Entity-Relationship (ER) Model

Lectures 5a + 5b — Design Phases, Entities, Attributes, Relationships, Cardinalities, Weak Entities

What is Data Modeling?

Data modeling is the process of creating a simplified graphical representation of a complex real-world database. It is the first step in designing a database. A data model acts as the blueprint — like an architect's plan before building a house.

Why Data Modeling Matters
It helps designers, programmers, and end users all communicate using a common visual language. Without a model, different people have different (and often incorrect) views of the data structure.

Database Design Phases

1
Requirements Collection

Interview users, study forms and documents, understand what data is needed and what operations will be performed.

2
Conceptual Design

Use the ER Model to create a conceptual schema — an ER Diagram that represents entities, attributes, and relationships without worrying about implementation.

3
Logical Design

Translate the ER Diagram into a relational schema (tables). Decide which attributes go in which tables. Apply normalization.

4
Physical Design

Decide physical layout — file storage, indexes, partitioning. Specific to the chosen DBMS (MySQL, Oracle, etc.).

ER Diagram Notation — Symbol Reference

Entity Sets

An entity is a real-world object — a person, place, thing, or event — that is distinguishable from all other objects. An entity set is a collection of similar entities sharing the same properties.

Examples
Entity Sets: STUDENT (set of all students), COURSE (all courses), INSTRUCTOR (all instructors)
Entity Instances: One specific student, e.g., Ali Ahmed with STU_NUM=001, is one entity instance.

Relationship Sets

A relationship is an association among two or more entities. A relationship set is a set of all relationships of the same type.

Example
Student 44553 (Peltier) — ADVISOR relationship — Instructor 22222 (Einstein)
The relationship set ADVISOR connects all student-instructor pairs where the instructor advises the student.

Relationships can also have attributes. For example, the ADVISOR relationship might have a "date" attribute recording when the advising started.

Mapping Cardinalities

Participation Constraints

Total Participation (Double Line)

Every entity in the set MUST participate in at least one relationship. Minimum cardinality = 1.
Example: Every student MUST have at least one advisor (total participation of student in advisor relationship).

Partial Participation (Single Line)

Some entities may not participate in any relationship. Minimum cardinality = 0.
Example: Not every instructor necessarily advises a student (partial participation of instructor in advisor relationship).

Weak Entity Sets

A weak entity cannot be uniquely identified by its own attributes alone. It depends on another (strong/identifying) entity for its existence and identification.

Strong Entity

Has its own Primary Key. Can exist independently. In ERD: single rectangle.

Weak Entity

No sufficient PK of its own. Depends on identifying entity. In ERD: double rectangle. Uses a discriminator (dashed underline) + identifying entity's PK for identification.

Classic Example
COURSE (course_id, title, credits) — Strong Entity — has own PK (course_id)
SECTION (sec_id, semester, year) — Weak Entity — sec_id alone is NOT unique (different courses can have the same sec_id)

To uniquely identify a SECTION, we need: {course_id, sec_id, semester, year}
The discriminator is sec_id. The identifying relationship is sec_course. SECTION cannot exist without COURSE.

In ERD: SECTION = double rectangle, sec_course = double diamond, sec_id = dashed underline.

Specialization and Generalization

Specialization (Top-Down)

Start with a general entity, then create specialized sub-groups. Lower entities inherit all attributes of the higher entity and add their own.
Shown with ISA triangle (reads as "is a").
Example: PERSON → STUDENT, EMPLOYEE, INSTRUCTOR

Generalization (Bottom-Up)

Combine similar entities that share common attributes into a higher-level entity. The reverse of specialization.
Example: STUDENT + EMPLOYEE (both have name, address) → PERSON

Overlapping: an entity can belong to multiple lower-level sets (e.g., someone can be both STUDENT and EMPLOYEE).
Disjoint: an entity can belong to only one lower-level set (e.g., an INSTRUCTOR and SECRETARY are disjoint).

📋 Chapter 5 Summary

  • The ER Model uses three concepts: Entity Sets (rectangles), Relationship Sets (diamonds), Attributes (ovals).
  • Attribute types: Simple, Composite, Single-valued, Multivalued, Derived, Key. Each has a different ERD symbol.
  • Cardinality: 1:1 (→→), 1:M (→—), M:N (——). Arrow = one, line = many.
  • Total participation (double line) = every entity must participate. Partial (single line) = some may not.
  • A Weak Entity has no PK of its own — uses discriminator + identifying strong entity's PK. Double rectangle + double diamond in ERD.
  • Specialization = top-down (general → specific). Generalization = bottom-up (specific → general). ISA triangle in ERD.
  • M:N relationships → create a new bridge table with both PKs. Multivalued attributes → create a separate table.

❓ Chapter 5 — Q&A

1What is the ER Model? What three basic concepts does it use?
The Entity-Relationship (ER) Model is a conceptual data model used to design databases by specifying the overall logical structure. It uses three basic concepts: (1) Entity Sets — a collection of similar real-world objects (e.g., STUDENT, COURSE). (2) Relationship Sets — associations among entity sets (e.g., STUDENT takes COURSE). (3) Attributes — properties of entities (e.g., StudentID, Name, DOB). The ER model is usually represented as an ER Diagram (ERD).
2List and explain all types of attributes in the ER Model with examples.
1. Simple: Cannot be subdivided. Example: Age, Gender.
2. Composite: Can be broken into sub-attributes. Example: Address → Street, City, ZIP.
3. Single-valued: Holds one value per entity. Example: CNIC, Registration Number.
4. Multivalued: Can hold multiple values. Example: Phone numbers, Degrees. Shown as double oval.
5. Derived: Calculated from other attributes, not stored. Example: Age derived from DOB. Shown as dashed oval.
6. Key Attribute: Uniquely identifies each entity. Shown underlined. Example: StudentID.
3Explain the four mapping cardinalities with examples.
1. One-to-One (1:1): Each entity in A is associated with at most one entity in B, and vice versa. Example: Each employee manages at most one store; each store has at most one manager.
2. One-to-Many (1:M): One entity in A can associate with many entities in B, but each B entity associates with at most one A entity. Example: One department has many employees, but each employee belongs to one department.
3. Many-to-One (M:1): Many A entities associate with one B entity. Mirror of 1:M.
4. Many-to-Many (M:N): Many A entities associate with many B entities, and vice versa. Example: A student can take many courses; a course can have many students. In ERD: undirected lines (—) on both sides.
4What is a Weak Entity Set? How is it different from a Strong Entity Set?
A Weak Entity Set is one that cannot be uniquely identified by its own attributes alone. It depends on an Identifying (Strong) Entity Set for its existence and identification. It uses a discriminator (dashed underline) attribute plus the PK of the identifying entity to form its unique identifier. In ERD: weak entity = double rectangle; identifying relationship = double diamond.
A Strong Entity Set has its own primary key and can exist independently.
Example: SECTION is weak (sec_id alone isn't unique across courses); COURSE is strong (course_id is sufficient).
5How is a Many-to-Many relationship converted to relational schemas?
A M:N relationship is converted by creating a new (bridge/junction) table that contains: the Primary Keys of both participating entity sets (as foreign keys), plus any descriptive attributes of the relationship itself.
Example: STUDENT M:N COURSE → create table ENROLLMENT(student_id, course_id, grade). Now: STUDENT 1:M ENROLLMENT and COURSE 1:M ENROLLMENT. The composite key {student_id, course_id} is the PK of ENROLLMENT.
6How are multivalued attributes handled when converting to relational schemas?
A multivalued attribute M of entity E is represented by creating a separate table that contains: (1) the Primary Key of entity E, and (2) one column for the multivalued attribute M. Each value of M becomes a separate row.
Example: Instructor has multivalued attribute phone_number → Create table: inst_phone(instructor_id, phone_number). An instructor with two phones has two rows in this table: (22222, 456-7890) and (22222, 123-4567).
7What is the difference between Specialization and Generalization?
Specialization is a top-down design process. You start with a general entity and create specialized sub-groups (lower-level entity sets) that have unique attributes or relationships. Example: PERSON → STUDENT, EMPLOYEE, INSTRUCTOR. Lower entities inherit all attributes of PERSON and add their own.
Generalization is a bottom-up process. You take several entity sets that share common features and combine them into a higher-level entity. Example: STUDENT + EMPLOYEE → PERSON (both share name, address). The two processes are inverses and represented the same way in ERD (ISA triangle).

ERD Details — Relationships, Cardinality & Design

Lectures 6a + 6b — Connectivity, Business Rules, Relationship Strength, Degree, Associative Entities

ERD as a Communication Tool

An ERD (Entity-Relationship Diagram) is a data modeling technique used to produce a conceptual data model of a database. It visually shows the logical structure so that both technical and non-technical people can understand it.

ERD Benefits
1. Shows database structure without requiring SQL knowledge
2. Improves communication between designers, managers, and end users
3. Acts as an "official blueprint" (like an architect's plan) — independent of any specific DBMS

Connectivity vs. Cardinality

Connectivity

The type/classification of relationship: 1:1, 1:M, or M:N. It tells you the general category but not the exact numbers.

Cardinality

The exact minimum and maximum occurrences. Written as (min, max). Example: (1, 4) means at least 1, at most 4. Written next to the entity in the ERD.

Example
Professor TEACHES Class — Connectivity: 1:M (one professor, many classes)
Cardinality on Professor side: (1,4) — each professor teaches 1 to 4 classes
Cardinality on Class side: (1,1) — each class is taught by exactly 1 professor

If cardinality is (1,N) → no upper limit on how many classes a professor can teach.

Relationship Strength

🔹 Weak (Non-Identifying) Relationship

The PK of the child/related table does NOT include any PK component from the parent entity.
Example: CLASS(CLASS_CODE, CRS_CODE, CLASS_SECTION) — CLASS_CODE is the PK, and CRS_CODE is just a FK (not part of PK). CLASS does not inherit COURSE's PK into its own PK.
In Crow's Foot: dashed line between entities.

🔸 Strong (Identifying) Relationship

The PK of the child/related table CONTAINS a PK component from the parent entity. The child is a weak entity.
Example: CLASS(CRS_CODE, CLASS_SECTION, CLASS_TIME) — The composite PK is {CRS_CODE + CLASS_SECTION}. CRS_CODE comes from the COURSE entity's PK.
In Crow's Foot: solid line between entities.

Existence Dependence

Existence-Dependent

An entity that cannot exist in the database without being associated with another entity. Has a mandatory FK.
Example: A DEPENDENT (child, spouse of employee) cannot exist in the HR database without an EMPLOYEE. If the employee is deleted, the dependent record is also removed.

Existence-Independent (Strong Entity)

An entity that can exist on its own, regardless of any relationship.
Example: A PART can exist in the database even if it has no VENDOR currently assigned to supply it.

Relationship Degree

Unary (1 entity) — Recursive

A relationship within a single entity. The entity relates to itself.
Example: EMPLOYEE "manages" EMPLOYEE — a manager is also an employee. Also: COURSE "is prerequisite of" COURSE.

Binary (2 entities)

Most common. A relationship between exactly two different entity sets.
Example: PROFESSOR teaches CLASS. STUDENT takes COURSE.

Ternary (3 entities)

Association among three different entity sets simultaneously.
Example: DOCTOR prescribes DRUG to PATIENT — one relationship involves all three entities at once.

Optional vs. Mandatory Participation

Optional Participation (circle "O" in Crow's Foot)

An entity occurrence does NOT need to have a corresponding entity occurrence in the relationship. Minimum cardinality = 0.
Example: A COURSE may generate a CLASS (optional — maybe the course isn't offered this semester).

Mandatory Participation (no circle)

Every entity occurrence MUST have a corresponding entity occurrence in the relationship. Minimum cardinality ≥ 1.
Example: An INVOICE must be generated by one CUSTOMER (mandatory — every invoice must have a customer).

Associative (Bridge) Entity

An Associative (Composite/Bridge) Entity is used to implement a M:N relationship. It contains the Primary Keys of both original entities plus any attributes of the relationship itself.

Step-by-Step: Resolving M:N into Two 1:M
Problem: STUDENT M:N COURSE (a student takes many courses; a course has many students)

Step 1: Create bridge entity ENROLLMENT with: StudentID (FK → STUDENT), CourseID (FK → COURSE)
Step 2: Add relationship attributes: Grade, EnrollmentDate
Step 3: The composite PK of ENROLLMENT = {StudentID, CourseID}
Step 4: Now M:N becomes two 1:M relationships:
    — STUDENT 1:M ENROLLMENT (one student, many enrollment records)
    — COURSE 1:M ENROLLMENT (one course, many enrollment records)

Schema: ENROLLMENT(StudentID, CourseID, Grade, EnrollmentDate)

Normalization

1NF → 2NF → 3NF → BCNF → 4NF → 5NF | Functional Dependencies | Anomalies | Lossless Decomposition

Why Normalize? — The Problem of Redundancy

Redundancy (storing the same data in multiple places) causes three serious problems:

🔴 Insertion Anomaly

You cannot insert data about one thing without also inserting data about something else.
Example: Can't add a new patron to the system until they've borrowed at least one book.

🟠 Update Anomaly

Updating data in one place requires updating it in multiple rows. Missing one creates inconsistency.
Example: If a patron moves, you must update their address in EVERY row where they appear.

🔴 Deletion Anomaly

Deleting one record accidentally deletes other needed information.
Example: If a patron returns all their books, you lose their address information entirely.

Solution
Normalization decomposes (splits) large tables into smaller, well-structured tables and defines relationships between them. The goal: every piece of data is stored in exactly one place.

Functional Dependencies (FD) — The Foundation

A Functional Dependency A → B means "A determines B": if two rows have the same value of A, they MUST have the same value of B.

sid → sname, address  |  cid → cname  |  {sid, cid} → grade

Types of Functional Dependencies

TypeDefinitionExample
Full Functional DependencyB depends on the ENTIRE composite key A — cannot remove any attribute from A and still determine B.{StudentID, CourseID} → Grade (you need BOTH to determine grade)
Partial DependencyB depends on only PART of a composite key. (Violates 2NF)In {StudentID, CourseID} → CourseName: CourseName depends only on CourseID, not StudentID
Transitive DependencyA → B and B → C, so A → C through a non-prime attribute B. (Violates 3NF)Reg → Province → City: City depends on Province (non-key), not directly on Reg
Multivalued DependencyX ⇒⇒ Y: for each value of X, Y values are independent of other attributes. (Violates 4NF)Restaurant ⇒⇒ Pizza AND Restaurant ⇒⇒ DeliveryArea

Armstrong's Axioms (Rules for deriving FDs)

AxiomRuleExample

AugmentationIf X → Y, then {X, Z} → {Y, Z}If cid → cname, then {cid, sid} → {cname, sid}

STEP 4 Boyce-Codd Normal Form (BCNF)

Rule: Must be in 3NF + For every non-trivial functional dependency X → Y, X must be a super key.

BCNF is stricter than 3NF. Most tables in 3NF are also in BCNF. Violations are rare but occur when a non-prime attribute determines part of a key.

Split into:
1. Student Table: (Student_ID, Student_Name) — Student_ID is PK, superkey ✅
2. Course Enrollment Table: (Student_ID, Course_Code, Grade) — {Student_ID, Course_Code} is PK ✅

Now every determinant in both tables is a super key → BCNF satisfied!

Rule: Must be in BCNF + No non-trivial multivalued dependencies unless the determinant is a super key.

A Multivalued Dependency X ⇒⇒ Y occurs when: for a given value of X, there is a set of Y values that is independent of all other attributes (Z). The Y values and Z values appear in all combinations.

Restaurant ⇒⇒ Pizza (each restaurant independently defines its pizza types)

These two facts are INDEPENDENT of each other → causes redundancy.

RestaurantPizza(Restaurant, Pizza) and RestaurantArea(Restaurant, DeliveryArea)

5NF — Fifth Normal Form

A table is in 5NF if every non-trivial join dependency is implied by its candidate keys. In simple terms: if you decompose the table into smaller tables and then join them back, you should get exactly the original table — no spurious (fake) rows are introduced.

Normalization Quick Reference Diagram

Lossless Decomposition

When you split a table (decompose it), you must be able to join the pieces back together and get exactly the original data — no extra rows, no missing rows. If joining creates fake (spurious) rows, it is a lossy decomposition and the decomposition is bad.

Lossless Rule
If R satisfies A → B, you can safely project R onto (A, B) and (A, C) and natural-join them back to get R without any spurious tuples. The common attribute A in both projections serves as the join key.

1What is Normalization? Why is it needed?
Normalization is the process of organizing a relational database to reduce data redundancy and improve data integrity. It works by decomposing large, poorly structured tables into smaller, well-structured ones while defining relationships between them. It is needed because redundancy causes three types of anomalies: (1) Insertion Anomaly: can't insert data about one entity without data about another. (2) Update Anomaly: changing one piece of data requires updating multiple rows; missing one causes inconsistency. (3) Deletion Anomaly: deleting one record unintentionally deletes other needed information.
2What is a Partial Dependency? How is it fixed?
A Partial Dependency occurs when a non-prime (non-key) attribute depends on only PART of a composite primary key, not the whole key. It violates 2NF.
Example: Table with PK = {StudentID, CourseID} — CourseName depends only on CourseID (part of PK). This is a partial dependency.
Fix: Remove the partially dependent attribute by creating a separate table. Move CourseName to a Course table with PK = CourseID. Keep only fully dependent attributes in the original table.
3What is a Transitive Dependency? How is it fixed?
A Transitive Dependency occurs when a non-key attribute A determines another non-key attribute B (A → B), and B is not determined by the PK directly but through A. This violates 3NF.
Example: Reg (PK) → Province → City. Province determines City, and Province is a non-key attribute. So City depends transitively on Reg through Province.
Fix: Create a separate table for the dependency. Split into: Student(Reg, Province) and Location(Province, City). Now City depends directly on Province (its own key), not transitively.
4Define 1NF, 2NF, 3NF, and BCNF clearly and concisely.
1NF: A table is in 1NF if every attribute contains only atomic (single, indivisible) values and every column has only one value per row. No multi-valued cells or repeating groups.
2NF: A table is in 2NF if it is in 1NF AND there are no partial dependencies — every non-prime attribute is fully functionally dependent on the entire primary key (not just part of a composite key).
3NF: A table is in 3NF if it is in 2NF AND there are no transitive dependencies — non-prime attributes depend only on candidate keys, not on other non-prime attributes.
BCNF: A table is in BCNF if it is in 3NF AND for every non-trivial functional dependency X → Y, X must be a superkey. Stricter than 3NF; handles cases where a non-prime attribute determines part of a key.
5What is BCNF? Give an example where a table is in 3NF but NOT BCNF.
BCNF (Boyce-Codd Normal Form) requires that for every non-trivial FD X → Y, X must be a superkey. It's stricter than 3NF and handles certain anomalies that 3NF does not.
Example: Enrollment(StudentID, StudentName, CourseCode, Grade) — PK = {StudentID, CourseCode}
FD: StudentID → StudentName (StudentID alone determines StudentName)
This is in 3NF (no transitive deps) but NOT BCNF because StudentID is not a superkey (it doesn't uniquely identify a row). Fix: split into Student(StudentID, StudentName) and Enrollment(StudentID, CourseCode, Grade).
6What is a Multivalued Dependency? Which Normal Form deals with it?
A Multivalued Dependency X ⇒⇒ Y occurs when, for a given value of X, the set of Y values is independent of all other attributes Z. This means X independently determines Y values and independently determines Z values, causing cartesian-product redundancy.
Example: Restaurant ⇒⇒ Pizza AND Restaurant ⇒⇒ DeliveryArea. For each restaurant, the pizza types and delivery areas are independent sets. Every pizza-area combination is stored.
4NF (Fourth Normal Form) addresses multivalued dependencies. Fix: split into two tables — one for Restaurant-Pizza pairs and one for Restaurant-DeliveryArea pairs.
7What is Lossless Decomposition? Why is it important?
Lossless Decomposition means that when you split (decompose) a table into multiple smaller tables, you can always join them back using a natural join and recover the original table exactly — without any extra (spurious) rows or missing rows.
Importance: If a decomposition is lossy, joining the tables creates fake tuples that didn't exist in the original data, leading to incorrect query results and data corruption.
Rule: If R satisfies A → B, then projecting R onto (A, B) and (A, C) and joining on A is always lossless. The common attribute A "anchors" the join correctly.

Relational Algebra

SELECT · PROJECT · UNION · INTERSECT · DIFFERENCE · PRODUCT · JOIN · DIVIDE

What is Relational Algebra?

Relational Algebra defines the theoretical (mathematical) way to manipulate data stored in relational tables. It is the formal foundation behind SQL. Every SQL query can be expressed using relational algebra operators.

Key Property — Closure
All relational algebra operators have the property of closure: applying any relational operator to one or more existing tables always produces a new table (relation). This means you can chain operations together.

The 8 Relational Operators

1. SELECT (σ) — Filter Rows

SELECT (also called RESTRICT) yields all rows from a table that satisfy a given condition. It is a horizontal subset — same columns, fewer rows.

σ condition (TABLE)
Example

σ salary > 50000 (EMPLOYEE)
Returns only the rows where salary exceeds 50000. All columns are kept.

SQL Equivalent
SELECT * FROM EMPLOYEE
WHERE salary > 50000;

2. PROJECT (π) — Filter Columns

PROJECT yields only the selected columns (attributes) from a table. It is a vertical subset — all rows, fewer columns. Duplicate rows are automatically removed.

π attribute_list (TABLE)
Example

π name, salary (EMPLOYEE)
Returns only the name and salary columns from EMPLOYEE. Other columns are dropped.

SQL Equivalent
SELECT name, salary
FROM EMPLOYEE;

3. UNION (∪) — Combine All Rows

UNION combines all rows from two tables into one, removing duplicate rows. Tables must be union-compatible: same number of attributes, same domains (compatible data types).

TABLE_A ∪ TABLE_B
Union-Compatible Means
Same number of columns AND each corresponding pair of columns has the same data type/domain. Example: You can UNION a list of students with a list of employees (both have name, ID, address columns of matching types).

4. INTERSECT (∩) — Common Rows Only

INTERSECT returns only the rows that appear in both tables. Tables must be union-compatible. The result contains only the intersection.

TABLE_A ∩ TABLE_B

5. DIFFERENCE (−) — Rows in One But Not Other

DIFFERENCE returns all rows in the first table that are NOT found in the second table. Tables must be union-compatible. Note: A − B ≠ B − A.

TABLE_A − TABLE_B
Important
Subtracting A from B is NOT the same as subtracting B from A. A − B gives rows in A that aren't in B. B − A gives rows in B that aren't in A.

6. PRODUCT (×) — Cartesian Product

PRODUCT returns all possible combinations (pairs) of rows from two tables. If Table A has m rows and Table B has n rows, the result has m × n rows. This is the foundation of JOIN.

TABLE_A × TABLE_B
Example
CUSTOMER (6 rows) × AGENT (3 rows) = 18 rows — every customer paired with every agent. Most combinations will be meaningless — that's why we apply JOIN conditions on top.

7. JOIN (⋈) — Combine Related Rows

JOIN is the most powerful relational operator. It combines rows from two tables based on a matching condition on related columns (usually a FK-PK pair).

Join TypeHow It WorksDuplicate Columns?

Natural Join — Step by Step

1
PRODUCT

Create a Cartesian Product of the two tables — all possible row combinations.

2
SELECT

Keep only the rows where the common attribute values are EQUAL (e.g., CUSTOMER.AGENT_CODE = AGENT.AGENT_CODE).

3
PROJECT

Remove the duplicate column (keep only one copy of the common attribute), giving the final joined table.

8. DIVIDE (÷)

DIVIDE finds all tuples in relation R that are related to ALL tuples in relation S. It answers queries like "Find all X that appear with EVERY Y." Rarely supported directly in SQL.

R ÷ S

📋 Chapter 8 Summary

  • Relational Algebra is the mathematical theory behind SQL. Operators have the property of closure.
  • SELECT (σ): filters rows (horizontal subset). WHERE in SQL.
  • PROJECT (π): selects columns (vertical subset). SELECT col1, col2 in SQL.
  • UNION (∪): combines all rows from two union-compatible tables, removes duplicates.
  • INTERSECT (∩): rows common to both tables. Tables must be union-compatible.
  • DIFFERENCE (−): rows in first table NOT in second. A−B ≠ B−A. Union-compatible.
  • PRODUCT (×): all combinations of rows. m rows × n rows = m×n rows.
  • Natural JOIN (⋈): 3 steps: PRODUCT → SELECT (matching) → PROJECT (remove duplicates). Real power of relational databases.
  • Outer Joins: include unmatched rows with NULLs. Inner join = matched only.

The output type (a relation) is the same as the input type. This allows operators to be chained — the output of one operation can be used as input to another.
2What is the difference between SELECT and PROJECT?
SELECT (σ) operates on ROWS — it returns a horizontal subset of a table. It filters rows based on a condition (like WHERE in SQL), keeping only rows that satisfy the condition. All columns are retained. Example: σ salary > 50000 (EMPLOYEE) — returns all employees with salary over 50000.
PROJECT (π) operates on COLUMNS — it returns a vertical subset of a table. It selects specific columns and discards the rest. Duplicate rows are automatically removed. Example: π name, salary (EMPLOYEE) — returns only the name and salary columns for all employees.
3What does "union-compatible" mean? Which operators require it?
Union-compatible means that two tables have: (1) the same number of attributes/columns, and (2) each corresponding pair of columns has the same domain (compatible data types).
The operators UNION (∪), INTERSECT (∩), and DIFFERENCE (−) all require union-compatible tables because they combine or compare rows across tables, which only makes sense if the columns represent the same types of data.
4Explain the three steps of a Natural Join.
Natural Join links two tables by matching equal values in their common column(s) and produces a result without duplicate columns. The three steps are:
Step 1 — PRODUCT: Compute the Cartesian product — every row of table A paired with every row of table B.
Step 2 — SELECT: From the Cartesian product, keep only the rows where the common column values are EQUAL (e.g., where CUSTOMER.AGENT_CODE = AGENT.AGENT_CODE).
Step 3 — PROJECT: Remove the duplicate common column — keep only one copy of the join column, giving the final clean joined table.
5What is the difference between Equijoin and Natural Join?
Both Equijoin and Natural Join use equality conditions to combine tables. The differences are:
Natural Join: automatically joins on all commonly named columns, eliminates duplicate columns from the result (you see the join column only once), and requires no explicit condition specification.
Equijoin: the join condition must be explicitly specified (e.g., ON table1.col = table2.col). Does NOT eliminate duplicate columns — the join column appears twice in the result (once from each table). The name "equijoin" comes from the equality (=) comparison operator used.
6What is an Outer Join? How does Left Outer Join differ from Right Outer Join?
An Outer Join returns matched records AND includes unmatched records from one or both tables, filling unmatched columns with NULL. It is NOT the opposite of inner join — outer join still includes all matched records plus the unmatched ones.
Left Outer Join: Returns ALL rows from the LEFT (first) table. Matched rows from the right table are included normally. For rows in the left table with NO match in the right, the right table columns show NULL.
Right Outer Join: Returns ALL rows from the RIGHT (second) table. Matched rows from the left table are included normally. For rows in the right table with NO match in the left, the left table columns show NULL.

5. CROSS JOIN — Cartesian Product

  • 2 CUSTOMERS × 2 ORDERS = 4 rows (if using small dataset)
  • Real dataset: 7 customers × 4 orders = 28 rows
  • Rarely used in practice — mainly for generating all possible combinations (e.g., generating a schedule)

CAP Theorem

Consistency · Availability · Partition Tolerance — Distributed Systems Design

What is the CAP Theorem?

The CAP Theorem (also called Brewer's Theorem, proposed by Eric Brewer in 2000, proved by Gilbert & Lynch in 2002) states that a distributed data system can simultaneously guarantee at most TWO of the three properties: Consistency, Availability, and Partition Tolerance. You cannot have all three at the same time.

What is a Distributed System?
A system where data is spread across multiple computers/servers in a network (e.g., Netflix's servers spread across the USA and Europe, Amazon's global database, social media backend). These systems must communicate across the network to work together.

Understanding Each Property

C — Consistency

Definition
Every read receives the most recent write or an error. All nodes (servers) in the distributed system see the SAME data at the SAME time. No matter which server you query, you always get the identical, up-to-date information.
Simple Explanation

When you update data on one server, the change is immediately seen by ALL other servers before any further reads are allowed. The data is always "consistent" everywhere — like one synchronized truth.

Real-World Example

Amazon product price: If a seller updates a product price from Rs.5,000 to Rs.4,500, and your friend opens the same product page milliseconds later, they should ALSO see Rs.4,500 — not the old price. Consistency = everyone sees the same price.

Inconsistency Example (what happens without C)
You and your friend both look at an Amazon product simultaneously. You see a price of Rs.5,000. Your friend on a different server sees Rs.4,500 because the update reached their server but not yours yet. This is inconsistency — two users see different data at the same time.

A — Availability

Definition
Every request receives a response (not necessarily the most current data). The system is ALWAYS up and running. Every request — read or write — gets a response, even if some servers are down or experiencing issues. The response may not be the most recent data.
Simple Explanation

The system never goes down. You always get SOME answer, even if it's slightly outdated. The priority is keeping the service online and responsive, not guaranteeing perfect data freshness.

Real-World Example

Netflix at 3 AM: Netflix must always be available for people to watch movies. If one server goes down, other servers handle the request. You might see a slightly outdated "recommended for you" list — but Netflix never shows you a "Service Unavailable" error.

P — Partition Tolerance

Definition
The system continues to operate even if some network messages between servers are delayed or dropped (i.e., a network partition occurs — servers temporarily cannot communicate with each other).
What is a Network Partition?

When the network connection between some servers fails (or experiences extreme lag), the servers are "partitioned" — split into groups that can't communicate. Think of it as an earthquake cutting the cable between your US servers and your European servers.

Real-World Example

Imagine the fiber cable between your New York data center and London data center is cut. A partition occurs. Partition-tolerant systems keep running in both locations even without communication between them.

Critical Insight — P is NOT Optional!
In any real-world distributed system, network failures WILL happen. Networks are unreliable — cables get cut, routers fail, packets get lost. This means every distributed system MUST be Partition Tolerant.

Therefore, the real choice is between C and A: When a partition occurs, do you want to prioritize Consistency (accurate data, possible downtime) or Availability (always online, possibly stale data)?

Aggregate Functions

COUNT · SUM · AVG · MIN · MAX · GROUP BY · HAVING · CASE WHEN · Window Functions

What are Aggregate Functions?

Aggregate functions perform a calculation on a set of values and return a single value. They summarize or group data — instead of returning every row, they return statistics about the data. Used with SELECT and commonly with GROUP BY.

Key Rule
Aggregate functions IGNORE NULL values (except COUNT(*)). They operate only on actual data. This means COUNT(*) and COUNT(column) can return different results if the column has NULLs.

The 5 Core Aggregate Functions

1. COUNT — Count Rows

COUNT returns the number of rows. There are two important forms:

COUNT(*)

Counts ALL rows, including rows with NULL values. Counts the total number of rows in the group.

COUNT(column)

Counts only rows where the specified column is NOT NULL. Ignores NULL values.

-- Count all students SELECT COUNT(*) AS Total_Students FROM Students; -- Count students who have a GPA recorded (not NULL) SELECT COUNT(GPA) AS Students_With_GPA FROM Students; -- Count DISTINCT values (unique departments) SELECT COUNT(DISTINCT Department) AS Num_Departments FROM Students;
  • Line 1: COUNT(*) — counts all 100 rows even if some GPAs are null → returns 100
  • Line 2: COUNT(GPA) — only 95 students have GPA recorded → returns 95
  • Line 3: DISTINCT — even if 100 students exist, only 5 unique departments exist → returns 5

2. SUM — Total of Values

SUM adds up all values in a numeric column. Ignores NULLs.

-- Total salary expense per department SELECT Department, SUM(Salary) AS Total_Salary FROM Employees GROUP BY Department;
  • SUM(Salary) adds all salary values within each department group
  • GROUP BY Department splits the calculation — one SUM per department
  • Result: one row per department showing that department's total payroll

3. AVG — Average Value

AVG computes the arithmetic mean of a numeric column. Ignores NULLs (they are not counted in the denominator).

-- Average marks per course SELECT CourseID, AVG(Marks) AS Average_Marks FROM Enrollment GROUP BY CourseID;
  • AVG(Marks) = sum of marks / count of non-null marks in that group
  • If a student has NULL for marks (absent), that row is skipped in the average calculation
NULL Warning for AVG
If 5 students are in a course, but 1 has NULL marks: AVG calculates the average of only 4 students' marks (not 5). This can make the average higher than expected.

4. MIN — Minimum Value

MIN returns the smallest value in a column. Works on numeric, text, and date columns.

-- Lowest salary in each department SELECT Department, MIN(Salary) AS Min_Salary FROM Employees GROUP BY Department; -- Earliest order date for each customer SELECT CustomerID, MIN(OrderDate) AS First_Order FROM Orders GROUP BY CustomerID;

5. MAX — Maximum Value

MAX returns the largest value in a column. Works on numeric, text, and date columns.

-- Highest mark scored in each course SELECT CourseID, MAX(Marks) AS Highest_Mark FROM Enrollment GROUP BY CourseID;

GROUP BY — Splitting Results into Groups

GROUP BY divides the result set into groups based on one or more columns. An aggregate function is then applied to each group independently, producing one result row per group.

Rule: Non-Aggregate Columns Must Be in GROUP BY
Any column in SELECT that is NOT inside an aggregate function MUST appear in the GROUP BY clause. Example: SELECT Department, AVG(Salary) — "Department" is not aggregated, so it must be in GROUP BY.
-- Count students per department with avg GPA SELECT Department, COUNT(*) AS Num_Students, AVG(GPA) AS Avg_GPA, MAX(GPA) AS Top_GPA FROM Students GROUP BY Department;
  • First, rows are split into groups by Department (CS, Math, Physics, etc.)
  • For EACH group separately: count rows, calculate average GPA, find maximum GPA
  • Result: one row per department with its own stats
  • Example result: CS | 45 students | 3.2 avg GPA | 4.0 top GPA

HAVING vs WHERE — Critical Difference

WHERE — Filters Rows BEFORE Grouping

WHERE is applied to individual rows before any grouping or aggregation takes place. You CANNOT use aggregate functions in WHERE.
Think: "Which individual rows should we include before we group?"

HAVING — Filters Groups AFTER Aggregation

HAVING is applied to groups AFTER aggregation. You CAN use aggregate functions in HAVING.
Think: "Which groups should we show after we've calculated the aggregates?"

-- WHERE vs HAVING: Find departments with avg salary > 50,000, only for active employees SELECT Department, AVG(Salary) AS Avg_Salary FROM Employees WHERE Status = 'Active' -- Step 1: Filter individual rows FIRST (only active employees) GROUP BY Department -- Step 2: Group remaining rows by department HAVING AVG(Salary) > 50000; -- Step 3: Filter groups (only dept with high avg salary)
  • WHERE Status = 'Active': first, removes all inactive employees from consideration — individual row filter
  • GROUP BY Department: groups remaining active employees by their department
  • AVG(Salary): calculates average salary within each department group
  • HAVING AVG(Salary) > 50000: removes department groups where average salary is ≤ 50,000
  • Final result: only departments with high-paying active employees
Common Mistake — Cannot use aggregate in WHERE!
WRONG: WHERE AVG(Salary) > 50000 — This causes an error because WHERE runs BEFORE grouping — there is no group to average yet!
CORRECT: HAVING AVG(Salary) > 50000 — HAVING runs AFTER the GROUP BY and aggregation are done.

CASE WHEN — Conditional Aggregation

CASE WHEN allows you to apply conditions INSIDE aggregate functions — essentially creating conditional counts or sums. Like an IF-THEN-ELSE inside an aggregation.

CASE WHEN condition THEN result [WHEN condition THEN result ...] [ELSE default] END
-- Count students by grade category in one query SELECT CourseID, COUNT(CASE WHEN Grade >= 90 THEN 1 END) AS A_Grade, COUNT(CASE WHEN Grade >= 80 AND Grade < 90 THEN 1 END) AS B_Grade, COUNT(CASE WHEN Grade < 60 THEN 1 END) AS Failed FROM Enrollment GROUP BY CourseID;
  • CASE WHEN Grade >= 90 THEN 1 END: returns 1 if grade ≥ 90, NULL otherwise
  • COUNT() of that expression: counts the 1s — which equals the number of A-grade students
  • COUNT() ignores NULLs: students with grades < 90 return NULL and are not counted in A_Grade
  • Result: one row per course showing how many students got each grade category
-- Find the course with the highest average marks (using nested aggregation / subquery) SELECT CourseID, AVG(Marks) AS Avg_Marks FROM Enrollment GROUP BY CourseID HAVING AVG(Marks) = ( SELECT MAX(AVG(Marks)) -- Inner query finds the max of all course averages FROM Enrollment GROUP BY CourseID );
  • Inner subquery: calculates AVG(Marks) for each course, then takes MAX of those averages
  • Outer query: finds the course whose average equals that maximum
  • This is a nested aggregation — aggregate of aggregates via subquery

Window Functions — Advanced (OVER, PARTITION BY)

Window functions perform calculations across a set of rows that are related to the current row without collapsing the rows into groups. They show both individual row data AND aggregate information together.

Key Difference from GROUP BY
GROUP BY collapses rows — you get ONE row per group. Window functions DO NOT collapse rows — you keep ALL rows but ALSO show aggregate information in each row.
-- Show each employee's salary AND their department average SELECT EmployeeName, Department, Salary, AVG(Salary) OVER(PARTITION BY Department) AS Dept_Avg_Salary, Salary - AVG(Salary) OVER(PARTITION BY Department) AS Diff_From_Avg FROM Employees;
  • OVER(PARTITION BY Department): "for each row, calculate the window over all rows in the same department"
  • AVG(Salary) OVER(...): returns the department average for each row — not one row per department
  • All individual employee rows are still shown (unlike GROUP BY)
  • Diff_From_Avg: shows how much each employee earns above/below their department average
  • Result: Each row shows employee name, their salary, AND their department's average salary side by side

SQL Execution Order — Full Reference

Execution Order Mnemonic: "From Where Groups Are Having Selections Limited"
① FROM → ② WHERE → ③ GROUP BY → ④ Aggregate functions evaluated → ⑤ HAVING → ⑥ SELECT → ⑦ ORDER BY / LIMIT

📋 Chapter 12 Summary

  • Aggregate functions compute a single value from a set of values: COUNT, SUM, AVG, MIN, MAX.
  • COUNT(*): counts all rows including NULLs. COUNT(col): counts non-NULL values only. COUNT(DISTINCT col): counts unique values.
  • GROUP BY: divides data into groups. Aggregate function is applied per group. Non-aggregated SELECT columns MUST appear in GROUP BY.
  • WHERE: filters INDIVIDUAL ROWS before grouping. Cannot use aggregate functions. HAVING: filters GROUPS after aggregation. CAN use aggregate functions.
  • Execution Order: FROM → WHERE → GROUP BY → Aggregates → HAVING → SELECT → ORDER BY.
  • CASE WHEN inside aggregate: creates conditional counts/sums. COUNT(CASE WHEN condition THEN 1 END) counts only rows meeting the condition.
  • Window functions OVER(PARTITION BY): calculate aggregates without collapsing rows. Each row retains its data plus sees the group aggregate.

1What is the difference between COUNT(*) and COUNT(column_name)?
COUNT(*) counts ALL rows in the table or group, including rows where the specified column has a NULL value. It literally counts every row.
COUNT(column_name) counts only the rows where that specific column is NOT NULL. NULL values are completely ignored.
Example: If a Students table has 100 rows but 10 students have no GPA recorded (NULL): COUNT(*) = 100, COUNT(GPA) = 90. The difference of 10 = number of students without a GPA. This distinction is very important when counting optional fields.
2What is the difference between WHERE and HAVING? Why can't you use aggregate functions in WHERE?
WHERE filters individual rows BEFORE the GROUP BY and aggregate functions are applied. It operates on raw table data, row by row.
HAVING filters groups AFTER the GROUP BY and aggregate functions have been applied. It operates on the grouped/aggregated results.
You CANNOT use aggregate functions in WHERE because at the time WHERE is evaluated, the grouping has NOT yet happened — there are no groups to aggregate. The DBMS hasn't computed COUNT(), AVG(), etc. yet. They are computed only AFTER GROUP BY, so HAVING (which comes after GROUP BY) is the correct place for aggregate conditions.
Example: WHERE AVG(salary) > 50000 — ERROR. HAVING AVG(salary) > 50000 — CORRECT.
3Write a query to find departments with more than 5 employees earning above Rs.30,000.
SELECT Department, COUNT(*) AS High_Earners FROM Employees WHERE Salary > 30000 GROUP BY Department HAVING COUNT(*) > 5 ORDER BY High_Earners DESC;
Explanation: (1) WHERE Salary > 30000 — first filters out all employees earning ≤ 30,000 (individual row filter). (2) GROUP BY Department — groups remaining employees by department. (3) COUNT(*) — counts employees in each department. (4) HAVING COUNT(*) > 5 — keeps only departments with more than 5 such employees. (5) ORDER BY — sorts by count descending.
4What is CASE WHEN? How is it used inside an aggregate function?
CASE WHEN is a conditional expression (like IF-THEN-ELSE) that evaluates a condition and returns different values based on the result. When used inside an aggregate function, it creates conditional aggregation — you can count or sum only rows that meet specific criteria.
Syntax: CASE WHEN condition THEN value ELSE other_value END
Example — Count male and female students in one query:
SELECT COUNT(CASE WHEN Gender='M' THEN 1 END) AS Male, COUNT(CASE WHEN Gender='F' THEN 1 END) AS Female FROM Students;
How it works: For each row, CASE WHEN returns 1 if gender matches, NULL otherwise. COUNT() counts the 1s and ignores the NULLs — giving the count for each gender.
5What is a Window Function? How does it differ from GROUP BY?
A Window Function performs a calculation across a set of related rows without collapsing them into a single output row. It uses the OVER() clause to define the "window" (set of rows) to compute over.
Key difference from GROUP BY: GROUP BY collapses all rows in a group into one result row — you lose individual row data. Window functions keep ALL rows AND add the aggregate calculation as an extra column per row.
Example: SELECT Name, Salary, AVG(Salary) OVER(PARTITION BY Department) AS DeptAvg FROM Employees;
This shows every employee's name and salary PLUS their department's average salary in every row — without reducing the number of rows. PARTITION BY is like GROUP BY inside the OVER() clause — it defines the subgroups for the window calculation.
6What is the correct SQL execution order? Why does it matter?
The correct SQL execution order is: ① FROM (identify tables and joins) → ② WHERE (filter individual rows) → ③ GROUP BY (group filtered rows) → ④ Aggregate functions evaluated (COUNT, AVG, etc.) → ⑤ HAVING (filter groups) → ⑥ SELECT (choose columns to display) → ⑦ ORDER BY / LIMIT (sort and limit output).
It matters because: (a) It explains why you can't use WHERE with aggregates (aggregates don't exist yet at step 2). (b) It explains why column aliases created in SELECT can't be used in WHERE or HAVING (SELECT happens at step 6). (c) Understanding this order helps write correct queries and debug errors logically.

Stored Procedures

What is a Stored Procedure?

A Stored Procedure (SP) is a named, pre-compiled group of SQL statements that is saved in the database and can be executed (called) repeatedly on demand — like a function or method, but for SQL.

Without Stored Procedures

Every time your application needs data, it sends raw SQL text to the server. The server must: parse the SQL, create an execution plan, optimize it, then execute it — ALL OVER AGAIN every single time.

With Stored Procedures

SQL is written once, stored in the database, and pre-compiled (execution plan cached). Every subsequent call just executes the pre-compiled plan directly — much faster and more secure.

Key Characteristics

Structure of a Stored Procedure

Header

Contains: procedure name, list of parameters (type: IN, OUT), any procedure options (DEFINER, SECURITY). The header defines the procedure's interface.

Body

Contains: the SQL statements to execute (enclosed in BEGIN...END). Can include variables, IF conditions, loops, error handling, and transaction statements.

Types of Parameters

Creating & Using Stored Procedures — Step by Step

Type 1: Simple Stored Procedure (No Parameters)

DELIMITER // CREATE PROCEDURE GetAllStudents() BEGIN SELECT * FROM Students; END // DELIMITER ; -- Execute it: CALL GetAllStudents();
  • DELIMITER //: Changes the statement delimiter from semicolon to // so MySQL doesn't misinterpret the semicolon inside the procedure as the end of the CREATE statement
  • CREATE PROCEDURE GetAllStudents(): Defines a procedure named GetAllStudents with no parameters
  • BEGIN...END: The procedure body — contains all the SQL to execute
  • DELIMITER ;: Restores the normal semicolon delimiter
  • CALL GetAllStudents(): Executes the procedure. Returns all students.

Type 2: Stored Procedure with IN Parameter

DELIMITER // CREATE PROCEDURE GetStudentsByDept(IN dept_name VARCHAR(50)) BEGIN SELECT StudentID, Name, GPA FROM Students WHERE Department = dept_name; END // DELIMITER ; -- Execute: pass a department name as argument CALL GetStudentsByDept('Computer Science'); CALL GetStudentsByDept('Mathematics');
  • IN dept_name VARCHAR(50): defines an input parameter named dept_name of type VARCHAR(50)
  • The WHERE clause uses dept_name like a variable — its value is whatever was passed in the CALL
  • First CALL: returns only CS students. Second CALL: returns only Math students. Same procedure, different results.
  • This shows reusability — one procedure handles different inputs

Type 3: Stored Procedure with OUT Parameter

DELIMITER // CREATE PROCEDURE CountStudentsInDept( IN dept_name VARCHAR(50), OUT total INT ) BEGIN SELECT COUNT(*) INTO total FROM Students WHERE Department = dept_name; END // DELIMITER ; -- Execute: OUT param is a user variable (prefixed with @) CALL CountStudentsInDept('Computer Science', @cs_count); SELECT @cs_count AS CS_Student_Count;
  • IN dept_name: input — the department to search
  • OUT total INT: output parameter — procedure will write the count into this variable
  • SELECT COUNT(*) INTO total: the INTO keyword stores the result directly into the OUT variable
  • @cs_count: a session variable. After CALL completes, @cs_count holds the count
  • SELECT @cs_count: reads and displays the value returned by the procedure

Type 4: Stored Procedure with Conditional Logic (IF)

DELIMITER // CREATE PROCEDURE GradeReport(IN marks INT) BEGIN IF marks >= 90 THEN SELECT 'Grade: A - Excellent!' AS Result; ELSEIF marks >= 80 THEN SELECT 'Grade: B - Very Good' AS Result; ELSEIF marks >= 60 THEN SELECT 'Grade: C - Average' AS Result; ELSE SELECT 'Grade: F - Failed' AS Result; END IF; END // DELIMITER ; CALL GradeReport(85); -- Returns: Grade: B - Very Good CALL GradeReport(55); -- Returns: Grade: F - Failed
  • IF...ELSEIF...ELSE...END IF: standard conditional block inside procedure body
  • Each ELSEIF checks the next condition only if all previous conditions were false
  • ELSE handles all remaining cases (marks < 60)
  • This shows procedural logic (not possible with basic SQL) inside a stored procedure

Type 5: Stored Procedure with Transaction (COMMIT / ROLLBACK)

DELIMITER // CREATE PROCEDURE TransferFunds( IN from_account INT, IN to_account INT, IN amount DECIMAL(10,2) ) BEGIN DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; -- If any error, undo ALL changes SELECT 'Transfer failed - rolled back'; END; START TRANSACTION; UPDATE Accounts SET Balance = Balance - amount WHERE AccountID = from_account; UPDATE Accounts SET Balance = Balance + amount WHERE AccountID = to_account; COMMIT; -- Save BOTH changes permanently SELECT 'Transfer successful'; END // DELIMITER ;
  • DECLARE EXIT HANDLER FOR SQLEXCEPTION: if ANY error occurs inside the transaction, automatically ROLLBACK
  • START TRANSACTION: begins the transaction — all following changes are provisional (not saved yet)
  • First UPDATE: deducts amount from sender's balance
  • Second UPDATE: adds amount to receiver's balance
  • COMMIT: only if BOTH updates succeed, make the changes permanent
  • ROLLBACK: if anything fails, undo BOTH updates — money is never "lost" between accounts
  • This guarantees ACID properties — either both happen or neither does

Type 6: Stored Procedure with Default Parameter Value

CREATE PROCEDURE GetTopStudents(IN num_students INT) BEGIN SET num_students = IFNULL(num_students, 10); -- Default to 10 if NULL passed SELECT * FROM Students ORDER BY GPA DESC LIMIT num_students; END; CALL GetTopStudents(5); -- Returns top 5 students CALL GetTopStudents(NULL); -- Returns top 10 (default)

Advantages of Stored Procedures — Detailed

⚡ Performance — Pre-compilation

The first time a stored procedure runs, the DBMS compiles and caches the execution plan. All subsequent executions skip the parsing and optimization step — they use the cached plan directly. Much faster than sending raw SQL each time.

🔒 Security — Least Privilege

You can grant EXECUTE permission on a stored procedure without giving users direct access to the underlying tables. Users can call GetStudentReport() without having SELECT permission on the Students table. This hides sensitive table structures.

🔁 Reusability — Write Once

The same stored procedure can be called from any application — whether it's a web app, mobile app, desktop program, or another stored procedure. Logic is defined once in the database, not duplicated in every application.

📦 Encapsulation — Business Logic in DB

Business rules (validation, calculations, constraints) live in the database layer — not scattered across multiple application programs. Changing a business rule only requires changing one stored procedure, not updating multiple apps.

🌐 Reduces Network Traffic

Without SP: Application sends 10 SQL queries → 10 round trips over the network. With SP: Application sends one CALL statement → one round trip → server executes all 10 queries internally. Dramatically reduces network load.

💳 Transaction Management

Stored procedures can wrap multiple SQL statements in a single transaction with COMMIT/ROLLBACK, ensuring ACID properties. Guarantees that related operations either ALL succeed or ALL fail — critical for banking and inventory systems.

Important Note — Naming Convention
Do NOT prefix your stored procedures with "sp_" (e.g., sp_GetStudents). In SQL Server, "sp_" is reserved for system stored procedures. If you use this prefix, SQL Server first searches the master database before your own database — causing performance issues and potential naming conflicts.

1What is a Stored Procedure? How is it different from a regular SQL query?
A Stored Procedure is a named, pre-compiled collection of SQL statements stored in the database that can be executed repeatedly with a single CALL statement.
Differences from a regular SQL query:
1. Stored vs. Transient: A regular query is typed and sent each time. An SP is saved in the DB permanently and just called by name.
2. Pre-compiled: Regular queries are parsed and optimized on every execution. SPs are compiled once and the plan is cached — subsequent calls are faster.
3. Parameterized: SPs accept parameters making them dynamic. Regular queries require rewriting for different values.
4. Security: You can grant EXECUTE on an SP without giving table-level access.
5. Procedural Logic: SPs can contain IF-ELSE, loops, variables, and transaction control — not possible in a simple SELECT.
2What are the three types of parameters in Stored Procedures? Explain each.
IN (Input): The calling program passes a value to the procedure. The procedure can read and use this value but cannot send a modified version back. This is the default parameter type. Use case: passing search criteria, insert values, filter conditions.
OUT (Output): The procedure sets the value of this parameter and returns it to the caller. The procedure cannot read the initial value. Use case: returning a count, a computed result, or a status code after the procedure runs.
INOUT (Input-Output): The caller passes a value in; the procedure can read it, modify it, and return the new value to the caller. Use case: incrementing a counter, transforming a value and returning it.

CREATE: CREATE PROCEDURE procedure_name(IN param1 TYPE, OUT param2 TYPE) BEGIN ... SQL statements ... END;
CALL: CALL procedure_name(value1, @output_variable);
ALTER (change metadata only): ALTER PROCEDURE procedure_name [characteristic];
(To change the body: DROP then recreate with CREATE PROCEDURE)
DROP: DROP PROCEDURE IF EXISTS procedure_name;

4List and explain four advantages of stored procedures.
1. Performance (Pre-compilation): Stored procedures are compiled once and the execution plan is cached. Subsequent executions reuse the cached plan — no repeated parsing or optimization. This is significantly faster than sending raw SQL each time, especially for complex queries.
2. Security (Least Privilege): You can grant users EXECUTE permission on a stored procedure without giving them direct access to the underlying tables. This protects sensitive data and table structures.
3. Reduces Network Traffic: Instead of sending multiple SQL statements over the network (10 queries = 10 round-trips), an application sends one CALL statement. All SQL runs on the server — only results are sent back. Reduces network load dramatically.
4. Reusability: A stored procedure is written once and can be called from any application (web app, mobile app, desktop, other procedures). Business logic doesn't need to be duplicated in every application.
5What is a transaction inside a stored procedure? Why is it important?
A transaction inside a stored procedure is a group of SQL operations wrapped between START TRANSACTION and COMMIT/ROLLBACK that guarantees all-or-nothing execution (ACID properties).
Syntax: START TRANSACTION; → execute multiple SQL operations → COMMIT (if all succeeded) or ROLLBACK (if any failed).
Importance: Ensures data integrity when multiple related operations must all succeed or all fail together. Example: A fund transfer involves two UPDATEs — deduct from sender AND add to receiver. If the second UPDATE fails (e.g., system crashes), without a transaction, money is deducted from the sender but never added to the receiver. With a transaction, both are rolled back — the sender keeps their money. This prevents data corruption in critical systems.
6What is the DELIMITER command and why is it needed when creating stored procedures?
The DELIMITER command changes the character(s) that MySQL uses to detect the end of an SQL statement. By default, MySQL uses the semicolon (;) as the statement terminator.
Problem: Stored procedure bodies contain semicolons at the end of each SQL statement inside BEGIN...END. If you don't change the delimiter, MySQL will misinterpret these internal semicolons as the end of the CREATE PROCEDURE statement — resulting in syntax errors.
Solution: Change the delimiter to something unusual (//) before creating the procedure, then restore it after:
DELIMITER // → write CREATE PROCEDURE with internal semicolons → END // → DELIMITER ;
Now MySQL only considers // as the statement end — the internal semicolons are treated as part of the procedure body.
7What does "pre-compilation" mean in the context of stored procedures?
When a stored procedure is first created (or first executed in some systems), the DBMS goes through these steps: (1) parses the SQL code for syntax errors, (2) validates object references (tables, columns exist), (3) creates an optimized execution plan (the most efficient way to run the query), and (4) stores (caches) this compiled execution plan in the database.
Pre-compilation means this work is done ONCE and stored. On all subsequent executions (every CALL), the DBMS skips steps 1-3 entirely and jumps straight to execution using the cached plan. This is much faster than regular SQL queries, which repeat parsing and optimization on every single execution — even if the exact same query text is sent each time.
